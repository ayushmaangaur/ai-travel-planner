# AI Travel Planner

A multi-agent AI travel planning system built with Python and Gemini. The project is being developed as a practical AI Engineering project, with a focus on agent orchestration, structured data, stateful conversations, testing, and eventually real-world APIs and A2A communication.

## Architecture

```text
User
  ↓
RootTravelAgent
  ↓
LLMService
  ↓
TravelRequest
  ↓
ConversationSession
  ↓
TravelRequestValidator
  ↓
┌──────────────┬──────────────┬──────────────┐
↓              ↓              ↓
FlightAgent  HotelAgent   WeatherAgent
↓              ↓              ↓
FlightRec.   HotelRec.    WeatherRec.
└──────────────┴──────────────┴──────────────┘
                    ↓
               TravelPlan
```

### Current Components

- **RootTravelAgent** — extracts travel requirements, maintains conversation state, validates requests, and orchestrates specialized agents.
- **LLMService** — provides the abstraction layer for Gemini and mock LLM responses.
- **ConversationSession** — maintains the current `TravelRequest` across multiple user messages.
- **TravelRequestValidator** — checks required travel information.
- **FlightAgent** — generates and ranks flight options based on budget and preferences.
- **HotelAgent** — generates and filters hotel recommendations.
- **WeatherAgent** — generates weather forecasts with defensive handling of malformed responses.
- **TravelPlan** — combines structured flight, hotel, and weather recommendations.

## TravelRequest

The current request model supports:

```text
current_location
origin
destination
days
budget
travelers
preference
```

`current_location` and `origin` are intentionally separate. If the user does not specify an origin but provides their current location, the Root Agent can use the current location as the trip origin.

The conversation session merges only newly provided non-null values, allowing conversations such as:

```text
User: I want to visit Japan.

Agent: How many days?

User: 7 days.

Agent: What's your budget?

User: ₹50,000.
```

## Multi-Agent Flow

Once a `TravelRequest` is complete:

```text
RootAgent
    │
    ├──→ FlightAgent
    │
    ├──→ HotelAgent
    │
    └──→ WeatherAgent
             │
             ↓
        TravelPlan
```

Each specialized agent returns a structured recommendation rather than plain text.

## Mock LLM Mode

Gemini API usage is expensive/limited during development, so the project supports mock responses.

Set:

```env
USE_MOCK_LLM=true
```

to develop without making Gemini API calls.

Set:

```env
USE_MOCK_LLM=false
```

to use Gemini.

The unit tests additionally patch both `google.genai.Client` and `LLMService.generate()` to ensure tests cannot accidentally consume API quota.


Run the test suite:

```bash
pytest -v
```

Current tests cover:

- Root Agent
- Flight Agent
- Hotel Agent
- Weather Agent
- Structured `TravelRequest`
- Structured `TravelPlan`
- Mock LLM execution
- Prevention of Gemini API calls during tests
- Individual agent failures
- Partial `TravelPlan` generation when an agent fails
- Error collection in `TravelPlan.errors`

## Current Design Decisions

- LLM functionality is isolated behind `LLMService`.
- Agents communicate using structured Python models.
- The Root Agent is responsible for orchestration rather than implementing specialized travel logic.
- Conversation state is maintained independently through `ConversationSession`.
- Specialized agents can eventually be replaced with different LLMs or external services without redesigning the entire system.
- Mock mode is used for development and testing to avoid unnecessary API calls.

## Known Limitations

### Simulated travel data

Flight, hotel, and weather information is currently generated by the LLM/mock system.

It is **not yet connected to real travel APIs**, so generated prices, availability, flight numbers, hotels, and forecasts should not be treated as real booking information.

### Budget handling

The current budget is used directly by individual agents. It does not yet represent a proper overall trip budget.

Eventually the system should allocate the total budget across:

```text
Flights
Hotels
Food
Transportation
Activities
Other expenses
```

### Error handling

Basic partial-failure handling exists. If one specialized agent fails, the Root Agent can return the remaining recommendations together with an `errors` list.

Further production-level retry, timeout, fallback, and API error handling is still required.

## Development Philosophy

The project is intentionally being built incrementally:

```text
Basic LLM
   ↓
Structured output
   ↓
Stateful Root Agent
   ↓
Specialized Agents
   ↓
Multi-Agent Orchestration
   ↓
Testing + Error Handling
   ↓
Real APIs
   ↓
A2A
   ↓
Backend API
   ↓
Frontend
```

The immediate priority is to make the backend reliable before introducing A2A communication or the frontend.
